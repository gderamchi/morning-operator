## Capture and semantic learning

Learn offers **Record a little of my morning** on iOS 27 and **Choose a recording or file** on all supported platforms. Capture begins only after the person starts the flow and confirms Apple’s picker. The importer reads only the selected local file, uses security-scoped access while reading, samples at most 24 video frames, and uses Vision to extract visible text. Fast transitions may be missed; OCR does not provide a historical touch stream or establish why the user acted. The selected source file remains the user's file. The app does not keep exported sampled frames. [Vision text recognition](https://developer.apple.com/documentation/vision/recognizetextrequest).

The structured extraction retains every requested sample before notes deduplication, including blank/decode/OCR failures, exact actual timestamps where available and labeled fallbacks otherwise. Bounded OCR bodies, IDs and metadata—not frame pixels—are saved with the latest observation. Source-truncated or omitted text is marked and excluded from context identification. Learn's optional **Recognize sampled screens** path selects an unchanged prefix of at most **320 characters and six whole nonempty lines** per eligible frame for separate bounded Foundation Models calls. The full source remains saved; optional `inputSelection` metadata records what was selected. Accepted quotations must occur in both the supplied excerpt and original frame. The revised pure preparation replay selected all **24 baseline samples and 2,217 characters**; that establishes input coverage, not correct recognition.

Unavailable, failed and completed-with-unknown outcomes remain distinct. The earlier Mac attempt reported model not ready with zero requests. The subsequent simulator attempt reported available but made **six failed requests, returned zero responses and retained 24 unknown decisions**. The app process's native log identified `operationNotAllowed: Simulator is not supported` in a required backend. This is a runtime support failure, not a finding that the content violated a policy or a model-abstention result. There is no physical-device context-model benchmark yet. [Benchmark evidence](OBSERVATION-BENCHMARK.md).

The OS 26 semantic path sends observation text to `SystemLanguageModel` and checks availability first. Selected imports require an explicit Suggest a routine action. In the revised native-recording flow, finalized media is processed when the app is foreground and idle; extracted text is persisted before automatic model analysis, and the resulting draft still requires review and approval. Dynamic guided-generation schemas constrain the response; validation then rejects unknown action categories, out-of-range durations, and evidence quotes absent from the supplied text. Every accepted proposal is unapproved. Model availability is a runtime state, not a consequence of the framework importing successfully. Manual setup remains available when the model is unavailable. [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel).

This implements one-observation interpretation. Multi-day habit clustering, confidence tracking, contextual exceptions, and general cross-app visual understanding are future work. No model-generated proposal is permission to perform an external effect.

### iOS 27 native recording

Apple now documents ScreenCaptureKit on iOS 27. Its sample presents `SCContentSharingPicker` for either the full display or the app's own content, then captures with `SCStream`. `SCRecordingOutput` encodes a recording to a file. A full-display stream surviving backgrounding uses the `screen-capture` background mode; microphone capture has its own audio-session/background requirements and follows the person's picker choice. The revised source implements a screen-only path with no microphone/camera, explicit Stop, selected 5/10/20/30-minute limits and a 256 MiB size bound. A shared owner survives dismissal of the app-owned Record/Learn sheets; a root status control remains. The Apple-owned picker/panel is distinct: automatic dismissal remains unverified, and no public dismissal API is established here. Finalized recordings are staged from the service callback; same-session clips can proceed to local extraction and an unapproved draft while the foreground app is idle, whereas a pending clip recovered on relaunch requires Retry; no separate Use action is normally required. Earlier XCTest and owner checks failed with an empty Learn field despite a success banner; those failures remain recorded in [PHASE-ONE](PHASE-ONE.md). A later owner-confirmed short clip established capture → OCR → persisted text → visible unapproved draft, with readable text surviving ordinary-app relaunch. The draft incorrectly treated setup/marketing copy as habits. A subsequent deterministic filter replay rejects that known input; it is not a new model abstention or a general accuracy pass. Long captures, interruption/recovery, protected content and broad reliability still require their own device checks. This native path is not the iOS 26 baseline. [Apple's iOS screen-capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios).

Apple describes ScreenCaptureKit as the successor to ReplayKit for streaming/mirroring, without requiring a broadcast extension on its supported newer platforms. Do not carry forward a blanket claim that system-wide screen capture always requires a ReplayKit extension. Imported recordings remain the fallback on older supported systems. [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit).

The latest extracted text/source, bounded frame OCR/metadata and optional context classification, including its input-selection metadata, share the local workspace's single observation slot. A readable import replaces the slot; editing notes invalidates attached frames/classification, and Clear removes them with the notes. Existing routine quotations remain. All-blank extraction does not overwrite the prior observation and does not trigger a proposal. Revised recovery retains app-owned raw media after blank/OCR/cancellation/persistence failure for Retry/Discard, and removes it after readable text and its evidence are successfully persisted or explicitly discarded. A later model/classifier failure does not need the raw video. Imported originals are preserved; no raw archive is added. The single retained recording lives in a local RecordingRecovery slot and is offered after relaunch. Clear observation does not discard that raw file; Discard recording does not erase previously saved evidence. Storage handoff/reload/removal have focused tests; broad physical interruption/retry/discard reliability remains pending. Saved-text relaunch and synthetic correction/clear journeys have their own narrower evidence in [PHASE-ONE](PHASE-ONE.md).

Neither the importer nor this picker path is an automatic morning first-pickup detector, invisible continuous monitor, or global tap-event feed. DeviceActivity first-use scheduling and the newer entitled usage-data API are documented options in the [observation plan](OBSERVATION-PLAN.md), but neither is implemented.

## One-time invitations

Review → Settings → Your next morning saves one future local invitation after an explicit Set invitation action. Its absolute instant stays fixed across time-zone travel. Notification delivery alone never starts a run: a person's tap creates a foreground request that waits for readiness and expires after 60 seconds; drafts open review and delayed requests reveal manual controls. No recording starts. Invitation consumption and the workspace receipt/run transition use separate durable writes, so a crash can require manual Start. The final simulator notification rerun passed after fixing main-actor completion of delegate callbacks; physical delivery, Siri and cold-launch/locked-phone entry are not established. ## Siri, voice, and speakers

The start and quick-capture intents use `supportedModes = .foreground(.immediate)`, which requests foreground execution after the system resolves parameters. Start additionally requests local-device authentication and routes through the shared entry policy; it cannot approve a draft or repeat an already-running operation. A custom `@Parameter` String can collect capture text; Siri may ask for a missing value. App Shortcuts include the application-name token in trigger phrases. The source routes a capture to review and returns a “ready for review” dialog; it does not claim the text has already been durably saved. Keep that distinction if the design changes. [Intent modes](https://developer.apple.com/documentation/appintents/appintent/supportedmodes), [Creating an App Intent](https://developer.apple.com/documentation/appintents/creating-your-first-app-intent), [App Shortcuts guidance](https://developer.apple.com/videos/play/wwdc2025/244/).

The app bundle must contain discoverable intent metadata. A Swift type-check alone does not prove Siri registration. App-only foreground execution avoids an extension's separate process, but does not make in-memory state durable; the review flow still needs its explicit Save. If background extensions are added, use appropriate shared storage and process coordination. OS 27's `LongRunningIntent` can extend certain tasks with progress reporting; it is not an unlimited background agent or the baseline for this short capture flow. [Runtime behavior](https://developer.apple.com/documentation/appintents/configuring-the-runtime-behavior-of-your-app-intents), [Shared data](https://developer.apple.com/documentation/technologyoverviews/shared-data), [LongRunningIntent](https://developer.apple.com/documentation/appintents/longrunningintent).

The new **Log an app transition** intent uses background execution and writes a separate local journal. Users configure per-app Is Opened/Is Closed automations themselves; currently supported choices are Instagram, TikTok and Snapchat. Callback time, app, transition, time zone, source and event ID are recorded. A supplied stable UUID deduplicates a deliberate retry. The shared actor serializes same-process writes without replacing the workspace; actual background process behavior and delivery still need verification. This action does not start recording or read app contents. [Apple App triggers](https://support.apple.com/guide/shortcuts/setting-triggers-apde31e9638b/ios).

The app now has speech output and an explicit [push-to-listen command turn](VOICE.md). It checks `supportsOnDeviceRecognition`, requires local recognition, displays transient text and accepts one final strict English/French command only after microphone release. It saves neither microphone audio nor the command transcript, and does not fall back to server recognition. This is source plus simulator entry/cancel evidence, not a real microphone trial or continuous conversation. Siri's own input path is separate and controlled by the system; local app storage does not imply every Siri request is processed offline. [Speech availability](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [On-device recognition requests](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition).

On iOS the app exposes a real `AVRoutePickerView`; the user selects an available output. There is no active Mac app workflow. AirPlay can deliver media to compatible speakers, but output routing is separate from input capture and does not establish access to a HomePod microphone. The route, audible result and behavior after disconnection still need a physical test. [AVRoutePickerView](https://developer.apple.com/documentation/avkit/avroutepickerview), [Supporting AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app).

Automatic room detection, person tracking and room-to-room transfer are not implemented. HomePod's documented cloud media integration targets media services and is not a generic microphone API for this app. [SiriKit Cloud Media](https://developer.apple.com/documentation/sirikitcloudmedia).

## EventKit permission and effect boundaries

Calendar reading requires full access; creation can use write-only access. Reminders uses full access for both reads and writes. Required purpose strings are `NSCalendarsFullAccessUsageDescription`, `NSCalendarsWriteOnlyAccessUsageDescription`, and `NSRemindersFullAccessUsageDescription` according to the enabled flow. Sandboxed macOS EventKit builds also need the calendars personal-information entitlement. [Event-store access](https://developer.apple.com/documentation/eventkit/accessing-the-event-store).

`ReminderService` never requests permission inside a read or create method. Its explicit permission methods must be called by the app's user-driven flow. Draft validation occurs before writes. New events have no recurrence, attendees or invitations; reminder alerts are explicit draft values. Reminder due components use a Gregorian calendar and the chosen time zone. [Creating events and reminders](https://developer.apple.com/documentation/eventkit/creating-events-and-reminders), [Reminder due components](https://developer.apple.com/documentation/eventkit/ekreminder/duedatecomponents).

The app retains a successful write receipt to prevent an ordinary retry from creating the same item again. A crash between the system write and local receipt persistence remains a recovery boundary: inspect Calendar/Reminders before retrying an uncertain effect. An EventKit success reports a local system-store save, not proof that a cloud account has completed syncing or that an alert was heard. Content deliberately saved to those apps follows their configured accounts and sync policies.

The date parser recognizes a limited grammar. “Tomorrow morning” means a proposed 09:00 on the next local calendar day; “in four hours” means four elapsed hours. Unsupported or ambiguous recognized expressions remain unresolved. The parser retains the original in its transient parse result; the saved capture contains the text the person reviewed and saved. The user can edit the proposed time or keep a reminder undated; there is no silent universal language/date understanding.

## Development automation remains a separate execution environment

`XCUIApplication(bundleIdentifier:)` and XCUI elements provide a genuine development route for inspecting and interacting with an installed app in a UI-test runner. That should be tested on the owner's paired device with the selected target, accessibility surface and expected postcondition. These testing APIs are not ordinary app-runtime permission to control other apps. [XCUIApplication bundle initializer](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/init(bundleidentifier:)), [XCUIElement](https://developer.apple.com/documentation/xcuiautomation/xcuielement).

The harness and its screenshots/result bundles can contain personal screen content. Keep them local and out of source control. A USB cable or successful pairing alone does not create a persistent app-to-app observation/control protocol. The current bounded tests are not yet the proposed continuous screen → semantic action → verified navigation loop.

The dedicated `MorningObservationBenchmark` scheme builds two synthetic fixture apps and its own controller target. They are separate from the shipping app and ordinary UI-test target. Their known foreground/scroll postconditions must remain separate from movie-only inference input. Fixture source or a simulator build does not establish a completed movie benchmark, native phone recording or context-model accuracy; current final runtime results remain pending.

## Voice choice and custom companions

Settings offers the installed Apple speech voices, a system-language default, and a short preview. Selection is persisted locally. This is AVSpeechSynthesizer speech output, not Foundation Models voice generation. A selected voice that is no longer installed falls back visibly to the default. Personal Voice access, a family member’s recordings and licensed actor voices remain a separate consent and feasibility project tracked in [issue #20](https://github.com/gibouu/morning-operator/issues/20). ## Evidence and future analytics

The existing day/week history measures runs inside Morning Operator. The separate App activity view in Review summarizes callbacks from configured apps, including returns after another tracked app. It is not integrated into a seven-day external-app usage model and has not been validated on a configured phone. Missing callbacks/unconfigured apps can hide intermediate activity; entry counts are not pickups or measured duration. The setup sheet now offers Clear recorded app activity; installed-device verification, export and automatic retention limits remain pending. Disabling Shortcuts automations stops future callbacks rather than removing saved entries.

Routine history remains distinct from these callback counts. Synthetic runs are excluded from personal averages; interrupted timing is unknown rather than guessed. The core data model can hold app observations with evidence references, coverage and optional counts, but the recorder does not yet populate a longitudinal per-app analytics store. A visible message does not prove the user read it, and OCR alone does not establish an exact reel, like or swipe count.

The `ObservationVideoEvidence` adapter now preserves frame order and validates identity decisions before producing `ObservationTrace`. Learn shows the latest recognized appearances, not measured app entries: generic headers can change within one app. The app leaves continuous capture coverage undeclared, so media duration does not become actual usage or a sampled-time estimate. Comparable-day reports preserve unknowns and per-metric denominators, but the latest persisted evidence is not a longitudinal library and no observed-habit average is wired into history. [Metric definitions and implementation boundary](OBSERVATION-METRICS.md).

[Issue #21](https://github.com/gibouu/morning-operator/issues/21) covers timestamped extraction, day/week aggregation, corrections and uncertainty. No sale, export pipeline, tracking SDK or third-party analytics collection is implemented. Any future aggregate-data product is a separate product/consent decision; raw recordings, private messages and HealthKit data are not a monetization feed in this prototype.
